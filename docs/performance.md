# 성능·저장 공간 점검

2026-09-11, Apple Silicon / macOS 26.6.2 / Swift 6.3.3.

추가 로그 처리, 그래프 계산, 화면 애니메이션, 이력 저장을 최적화했고 프로젝트 용량을 약 528MB → 85MB로 줄였습니다. 이후 오늘 상세 기록과 과거 일별 요약을 분리했습니다. 한도 계산 기준은 유지하며, 저장 형식은 검증 후 자동 이전합니다.

## 재현 가능한 계산 성능

1차 최적화에서 동일한 합성 데이터를 변경 전후 소스에 각각 `swiftc -O`로 컴파일해 번갈아 3회 실행한 중앙값입니다. 16,578,893바이트 JSONL에 토큰 이벤트 1,000개를 넣고, 마지막에 161바이트 이벤트 하나를 추가했습니다. 그래프는 관측 20,000건의 일별·시간별·15분별 집계를 묶어 20회 반복했습니다.

| 측정 | 변경 전 | 변경 후 | 효과 |
| --- | ---: | ---: | --- |
| 로그 최초 읽기 | 234.058ms | 114.552ms | 약 51% 감소 |
| 변경 없는 조회, 10회 평균 | 1.562ms | 1.390ms | 캐시 성능 유지 |
| 161바이트 추가 후 조회 | 220.070ms | 2.044ms | 약 99% 감소 |
| 추가 후 파일 읽기량 | 전체 약 16.6MB | 16,545바이트 | 경계 확인 + 추가분만 읽기 |
| 대량 그래프 집계, 20회 합계 | 923.766ms | 111.118ms | 약 88% 감소 |
| 그래프 검증 합계 | 1602.960000 | 1602.960000 | 계산 결과 일치 |

`make benchmark`로 현재 구현을 다시 측정할 수 있습니다. 실행 파일은 `.build/checks`에 덮어쓰며, 합성 로그는 임시 폴더에서 만들고 자동 삭제합니다. 이번 비교 원자료와 테스트 출력은 `.build/performance`에 있습니다. 시간 수치는 시스템 부하에 따라 달라지며 회귀 검증은 시간 임계값 대신 실제 읽기량과 계산 결과를 확인합니다.

## 실제 실행 부하

- 수정 전 실행 중인 앱에서 CPU 5.6~10.0%를 관측했고, 스택 샘플에서 SwiftUI 레이아웃·표시 갱신이 반복됐습니다. 작은 점의 `repeatForever` 애니메이션이 매 프레임 SwiftUI를 갱신하던 부분을 Core Animation의 레이어 투명도 애니메이션으로 바꿨습니다. 창이 보이지 않으면 중지하고, 동작 줄이기에서는 정지한 점을 표시합니다.
- 수정 후 실제 앱 대기 구간은 CPU 0.0%, 물리 메모리 약 39~41MB였습니다. 표시 중인 별도 샘플 창에서도 10초간 CPU 0.0~0.1%, 약 54MB를 관측했습니다. 서로 다른 실행 수명의 짧은 표본이므로 엄밀한 메모리 절감률이나 장기 배터리 수명으로 환산하지 않습니다.
- 최종 실제 로컬 조회는 오늘 수정된 43개 파일, 약 112MB를 0.35초에 읽었으며 변경 없는 재조회에서는 파일 본문을 0바이트 읽었습니다. 조사 초반의 기존 구현은 당시 약 104MB를 1.85초에 처리했습니다. 실제 로그가 계속 늘어나는 환경이므로 정량 비교에는 위 합성 벤치마크를 사용합니다.
- 실제 서버 조회도 성공했고 조회용 자식 프로세스는 종료됐습니다. 네트워크 응답 시간은 외부 서비스에 좌우됩니다. 기본 5분 주기는 유지하고, 한도 카드에서는 서버 토큰 요약과 로컬 로그 집계를 생략합니다. 토큰 카드 전환은 최근 결과를 재사용하고, 최초 조회·갱신 간격 경과·날짜/시간대 변경 시 필요한 조회를 시작하며 동시 새로고침은 하나로 합칩니다.

## 디스크와 데이터 증가량

용량은 `du -sh`의 반올림 값입니다.

| 영역 | 조사 시작 | 1차 정리 후 | 내용 |
| --- | ---: | ---: | --- |
| 프로젝트 전체 | 528MB | 85MB | 소스·문서·Git·빌드·앱 포함 |
| `.build` | 502MB | 61MB | 디버그/릴리스 모듈 캐시, 인덱스와 구형 미리 보기 앱 정리 |
| `dist` | 4.5MB | 2.3MB | 구형 `Cocount.app` 제거, 최신 `Co-Count.app` 유지 |
| `docs` | 4.6MB | 4.6MB | 기존 문서·이미지 유지 |

컴파일러 캐시와 인덱스만 약 439MB였으며 재생성이 가능합니다. `make clean-cache`는 이 둘만 삭제하고, 다음 컴파일이나 IDE 사용 시 다시 생성될 수 있습니다. 매번 자동 삭제하지 않으므로 평소 증분 빌드 속도를 유지합니다. 구형 미리 보기 앱을 정리하면서 과거 소스 백업은 보존했습니다.

일별 요약 분리 전 Co-Count의 실제 설정 파일은 점검 당시 3,382바이트였고, 그 안의 한도 이력 33건은 2,950바이트, 기간 이력은 85바이트였습니다. 이 당시에는 최근 8일·최대 20,000개 관측점을 하나로 보관했습니다. 현재는 오늘 상세 기록과 과거 8일 요약을 분리하며, 기간 기록은 계정별 현재와 과거 두 기간을 유지합니다.

변동 없는 8일을 5분 간격으로 관측한 동일 데이터에서는 **2,305건 / 193,638바이트 → 385건 / 32,358바이트**로 약 83% 줄었습니다. 30분 안의 같은 잔여율·같은 리셋 구간에서 중간 점만 제거하므로 관측 시간과 0% 사용 구간은 유지합니다. 증가·감소·리셋·누락·긴 공백은 합치지 않습니다. 실제 감소가 계속되는 데이터에서는 기존의 상세 관측을 보존하므로 이만큼 줄어들지는 않습니다.

아래는 일별 요약 분리 전의 비교 기준입니다. 모든 갱신에 사용률이 변한다고 가정한 1개 한도 합성 데이터의 8일 보관량을 나타냅니다. 이는 디스크에 매일 누적되는 쓰레기 데이터가 아니라 보관 중인 이력 크기입니다.

| 갱신 간격 | 관측 수 | 저장 크기 추정 | 하루 전체 재인코딩량 추정 |
| --- | ---: | ---: | ---: |
| 1분 | 11,521 | 942KB | 1.36GB |
| 5분 | 2,305 | 188KB | 54MB |
| 15분 | 769 | 63KB | 6MB |

재인코딩량은 모든 갱신에서 이력 전체를 직렬화한다는 계산값이며 실제 SSD 쓰기량과 다릅니다. UserDefaults의 쓰기 병합과 한도 개수에 따라 달라집니다. 직렬화는 전용 actor로 옮겼고, 활성 계정의 이력을 매번 다시 디코딩하지 않으며, 같은 기간 정보는 다시 저장하지 않습니다.

로컬 토큰 추정 캐시는 메모리에만 존재합니다. 카드 전환·숨김에도 유지해 다음 집계에서 변경 없는 파일과 추가된 로그를 재사용하며, 일자·시간대 변경 또는 샘플/실제 모드 변경 시 초기화합니다. 대화 본문을 저장하는 새 캐시나 로그 파일은 만들지 않습니다. 조사 당시 Codex의 `sessions`·`archived_sessions`에 있던 약 989MB의 원본 기록은 사용자의 Codex 데이터이므로 보존했습니다. app-server는 공유 Codex 캐시·SQLite 상태를 갱신할 수 있습니다. 실제 조회 전후 공유 WAL의 소규모 변화가 있었지만 다른 Codex 작업도 실행 중이어서 Co-Count만의 생성량으로 귀속하지 않았습니다.

앱 묶기는 새 임시 디렉터리에서 수행해 오래된 리소스를 남기지 않습니다. 바뀌지 않은 아이콘은 재사용하고 임시 iconset·작업 디렉터리·스냅샷용 설정은 작업 종료 시 정리합니다. Documents의 File Provider가 붙이는 Finder 메타데이터 때문에 서명 검증이 실패하는 경우에는 생성한 앱의 메타데이터만 최대 세 번 정리하고 엄격한 검증을 다시 수행합니다.

## 정확성·검증 범위

1차 최적화 검증: Core 36개 + 당시 UsageStore의 비동기 갱신 4개, 총 40개 통과. 현재 일별 요약·토큰 캐시까지 포함한 검증은 아래 결과를 참고하세요. 로그 추가·미완성 줄·잘림·동일 크기 교체·같은 파일의 확대 재작성·큰 줄 복구·날짜 변경·취소, 복사된 이벤트 중복 제거, 계정 분리·재시작 복원·만료 정리, 유휴 구간 압축, 기준 계산식과 집계 일치, DST·리셋·누락·긴 공백을 확인했습니다.

릴리스 빌드, 반복 앱 빌드, 로컬 서명, Info.plist 검증을 통과했습니다. 라이트·다크·토큰 스냅샷을 시각 확인했고 실제 샘플 창에서 토큰/한도 전환, 주간/5시간 기준, 어제 날짜 선택을 확인했습니다. 최종 실제 앱을 재시작했습니다.

증분 읽기는 Codex의 append-only 로그를 전제로 파일 식별자·크기·수정 시각과 앞/뒤 최대 4KiB 해시를 확인합니다. 파일 중간만 임의 수정하면서 크기를 늘리고 양쪽 경계를 보존하는 편집까지 검출하는 전체 파일 검증은 아닙니다. 그런 수동 편집 후에는 앱을 재시작하면 전체 재집계합니다. 새 파일은 처음 한 번 전체를 읽으며, 파일 목록 탐색은 여전히 전체 로그 경로 수에 비례합니다.

실제 잠자기·복귀, 장시간 연속 실행, Intel Mac과 macOS 14의 직접 실행 시험은 이번 범위에 포함하지 않았습니다.


## 오늘 상세 기록과 과거 일별 요약 분리

같은 **오늘 + 과거 8일(9개 날짜)**, 한도 1개, 사용률이 계속 변하는 데이터를 생성해 실제 파일 저장량을 비교했습니다. 1분·5분·15분 모두 과거 요약은 8개 파일, 합계 **14,192바이트(약 14KB)**로 같습니다. 평소 갱신에서는 오늘 파일만 쓰고 과거 파일의 내용·수정 시각은 그대로 유지됩니다.

| 간격 | 모두 상세하게 저장한 9일 | 오늘 파일 | 과거 8일 파일 | 현재 전체 | 평소 갱신의 과거 파일 쓰기 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1분 | 1,255,212B | 139,799B | 14,192B | **153,991B** | **0B** |
| 5분 | 251,058B | 28,464B | 14,192B | **42,656B** | **0B** |
| 15분 | 83,288B | 9,875B | 14,192B | **24,067B** | **0B** |

전체 보관량은 각각 약 88%·83%·71% 줄었습니다. 오늘 파일에는 자정 연결 기준점 하나와 검증용 추가 갱신 한 건이 포함돼 상세 관측 수는 1,442·290·98건입니다. 남은 비율의 소수 자릿수, 한도 수, 시간대에 따라 정확한 바이트 수는 달라집니다.

20회 반복한 원시 이력 객체 직렬화의 회당 평균은 1분 데이터 **49.8 → 5.5ms**, 5분 **10.0 → 1.1ms**, 15분 **3.3 → 0.4ms**였습니다. 최초 이전은 각각 약 78·26·17ms로 한 번만 발생했습니다. 시스템 부하에 따라 시간은 달라지며, 파일 크기와 과거 파일 쓰기 0바이트는 실제 저장 결과입니다. 아래 명령으로 재현할 수 있습니다.

```bash
make benchmark-history
```

하루 누적 처리량은 실제 앱을 24시간 관측한 수치가 아닙니다. 오늘 파일이 자정부터 점차 늘어나는 것을 감안하면, 위 파일 크기 기준 재인코딩량은 대략 1분 **101MB/일**, 5분 **4.2MB/일**, 15분 **0.5MB/일**입니다. 별도로 하루 요약 파일 약 1.8KB를 한 번 만듭니다. 이전의 85MB·3.4MB·0.4MB는 구현 전 관측당 바이트 수를 가정한 추정치였으며, 이 표는 실제 인코딩 크기에 기반합니다. 이는 실제 SSD 쓰기량이나 추가로 누적되는 저장 용량을 뜻하지 않습니다. 전체 앱 CPU·네트워크 사용량의 감소율과도 다릅니다.

구현은 `LimitUsageDay`의 바이너리 property list 안에 사용률과 관측 시간을 각각 64비트 숫자로 보관합니다. 96개 구간은 하루 약 1.8KB이며, DST에는 92·100개 등 실제 하루 길이를 따릅니다. 주간·5시간 한도는 따로 저장하고, 합계는 100%를 넘어도 잘리지 않습니다. 누락 구간과 0% 사용은 관측 시간으로 구분합니다.

새 요약 파일은 UUID로 식별하고 SHA-256 검사값으로 손상을 확인합니다. 먼저 요약을 저장·검증한 후, 오늘 상세 기록과 요약 파일 목록을 담은 `today.json`을 원자적으로 교체합니다. 이 파일의 목록에 포함된 요약만 읽으므로 중간 종료로 생긴 파일은 기존 이력에 섞이지 않습니다. 성공 후 이전 UserDefaults 키와 만료/미참조 요약을 정리합니다. 처리 가능한 저장 오류에서는 미완료 요약을 즉시 정리해 재시도마다 파일이 쌓이지 않게 하며, 비정상 종료로 남은 미참조 자료도 다음 성공 저장 또는 보관 기한 정리에서 제거합니다. 저장 실패 중에는 상세 기록을 메모리에 유지하고 다음 조회에서 다시 저장합니다. 실패가 계속돼도 상세 기록은 최대 9일·20,000개로 제한합니다. 읽기 오류가 있으면 기존 파일을 덮어쓰지 않으며, 현재 한도 조회는 계속 표시하고 하단에서 이력 재시도가 필요함을 알립니다.

마감은 자정을 넘는 첫 관측을 받은 뒤 수행해 직전 관측부터 자정까지의 감소분도 반영합니다. 이미 요약한 시간 구간은 오늘 원본 계산에서 제외해 중복 계산을 막습니다. 시간대 변경 시 요약의 절대 시간을 새 날짜 구간에 배치하며, 분할된 날짜 구간이 추가될 수 있습니다. 원본을 요약한 뒤에는 과거 1분 단위 재분석이나 다른 추정 규칙으로의 완전한 재계산은 할 수 없습니다.
